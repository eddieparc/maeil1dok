## Required environment variables

### Django/OCI

- `SENTRY_DSN` — blank disables Sentry locally.
- `SENTRY_ENVIRONMENT` — use `production` on OCI.
- `SENTRY_RELEASE` — optional deploy/revision identifier.
- `SENTRY_TRACES_SAMPLE_RATE` — default `0`; set deliberately after volume review.
- `SENTRY_SEND_DEFAULT_PII` — default `false`.

### Nuxt

- `NUXT_PUBLIC_SENTRY_DSN` for browser/client reporting.
- `SENTRY_DSN` or `NUXT_PUBLIC_SENTRY_DSN` for server reporting.
- `NUXT_PUBLIC_SENTRY_ENVIRONMENT`, `NUXT_PUBLIC_SENTRY_RELEASE`, `NUXT_PUBLIC_SENTRY_TRACES_SAMPLE_RATE`.
- `SENTRY_ORG`, `SENTRY_PROJECT`, `SENTRY_AUTH_TOKEN` only in CI/Vercel when uploading sourcemaps.

## Probe contracts

- Django uptime: `GET /health/` returns HTTP 200 with `checks.database.status=ok`. On database failure it returns HTTP 503 with only `checks.database.status=error` in the public body; exception detail is recorded in the `config.health_views` ERROR log and routed to OCI container logs + Sentry project `maeil1dok-django`.
- Django readiness: `GET /ready/` returns HTTP 503 when the database check fails, exposing only `checks.database.status=error` in the public body; the root cause is recorded in the `config.health_views` ERROR log. The response includes `checks.send_due_notification_reminders` and `checks.generate_hasena_summary`. Reminder readiness returns HTTP 503 when `send_due_notification_reminders` heartbeat is older than 15 minutes. It also returns HTTP 503 with `status=error` when the latest fresh reminder heartbeat recorded a failed run; failure detail stays in task logs and `send_due_notification_reminders failed` Sentry events and is never exposed in the public readiness payload, which carries only sanitized status/timing fields (`last_run_at`, `age_seconds`, `timeout_seconds`, `unknown_since`, `unknown_age_seconds`, `grace_seconds`). Legacy bare-datetime reminder heartbeats from prior deploys are still accepted and treated as `ok` when fresh. A missing reminder heartbeat starts a 15-minute grace marker (`unknown_since`) on first observation: `/ready/` returns HTTP 200 with `status=unknown` during the grace window so fresh deploys do not fail readiness before beat starts, then returns HTTP 503 with `status=missing` once the missing heartbeat exceeds the 15-minute grace. A confirmed fresh reminder heartbeat (`ok`) clears the reminder grace marker. Hasena summary readiness is enforced only Monday-Saturday 00:00-05:59 KST; outside that window, including Sunday early morning, `generate_hasena_summary.status=not_scheduled` and never fails readiness. Inside the scheduled window, missing, malformed, or previous-window heartbeat payloads start or reuse that window's 15-minute unknown grace and then become `missing`; stale unknown markers from earlier windows are reset. A previous-window heartbeat opens the next window as `unknown`, not immediate `stale`. A current-window heartbeat older than 15 minutes returns `stale` with HTTP 503. A fresh current-window heartbeat is classified by its recorded `status`: `success` (and benign `skipped` runs whose `reason` is `already_generated` or `summary_exists`) return `ok` with HTTP 200 and clear the Hasena unknown marker, while `failed`, `error`, or `pending` return that same status with HTTP 503 so a failed or still-incomplete generation attempt fails readiness instead of appearing green. A fresh heartbeat with an unrecognized or missing `status` falls back to the current-window unknown/`missing` grace path. The public Hasena payload carries only sanitized status/timing fields and never exposes the cached `reason`, `error`, exception text, `video_id`, or raw heartbeat payload; failure detail stays in task/cron logs, Sentry events, and cache internals.
- Django readiness cache/Redis failure: when a heartbeat readiness check cannot reach the cache backend (Redis outage, connection reset, or any exception raised while reading `send_due_notification_reminders` or `generate_hasena_summary` heartbeat state), `/ready/` returns HTTP 503 with root `status=degraded` and the affected check reduced to sanitized `status=error`. Redis URLs, hostnames, cache keys, cache payloads, exception messages, and tracebacks are never placed in the public body; the detailed exception is emitted once per affected check as a `config.health_views` ERROR log (`Readiness heartbeat cache check failed (check=...)`) routed to OCI container logs and Sentry project `maeil1dok-django`. This is intended: reminder and Hasena dead-man checks cannot be trusted without cache access, so a cache blip explicitly degrades readiness.
- Django readiness Web Push delivery: `/ready/` includes `checks.web_push_delivery` so an external monitor can catch silently skipped push delivery. `status=ok` (`configured=true`) means Django holds complete VAPID sender config (`WEB_PUSH_VAPID_PUBLIC_KEY`, `WEB_PUSH_VAPID_PRIVATE_KEY`, `WEB_PUSH_VAPID_SUBJECT`). When VAPID config is incomplete, `status=inactive` (`configured=false`, `active_subscriptions=false`) means no enabled push subscriptions exist so readiness stays HTTP 200; `status=error` (`configured=false`, `active_subscriptions=true`) means at least one enabled push subscription exists while delivery is disabled, so `/ready/` returns HTTP 503 with root `status=degraded`. `status=unknown` (`configured=false`) means subscription state was not checked because the database probe already failed; the database error drives the HTTP 503 in that case and no `NotificationPushSubscription` query runs. When the database probe succeeds but the active-subscription existence query itself raises (table/schema/permission/read outage), `status=error` (`configured=false`, `reason=subscription_probe_unavailable`) is returned and `/ready/` degrades to HTTP 503; the raw table name, hostname, SQL/provider error, and traceback go only to a single `config.health_views` ERROR log (`Readiness Web Push delivery check failed`) routed to OCI container logs and Sentry, never to the public body. The public payload carries only sanitized `status`, `configured`, and either `active_subscriptions` or `reason` fields; it never exposes VAPID values, subscription endpoints, `p256dh`, `auth`, user IDs, subscription IDs, or subscriber counts.
- Nuxt uptime: `GET /api/health` returns HTTP 200 with `status=ok` when production `public.apiBase` is a valid non-local HTTP(S) origin. It returns HTTP 503 with `status=degraded` when production `public.apiBase` is blank, malformed, an unsupported protocol, a non-origin value (credentials, path other than `/`, query string, or fragment), or a local/loopback host (`localhost`, `127.*`, `0.0.0.0`, `::1`). A missing `internalApiBase` is warning-only and never degrades root health. The public payload exposes only sanitized status values, `configured` booleans, reason codes, and the sanitized `public_origin`; it never leaks raw API-base values, credentials, paths, query strings, fragments, headers, tokens, secrets, or internal API-base URLs.
